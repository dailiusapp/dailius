# Database Schema

## Purpose

This document defines the core data model for Dailius.

It describes the business entities that make up the application. The implementation may evolve over time, but these concepts should remain relatively stable.

The schema is intentionally designed for the MVP and should avoid unnecessary complexity.

---

# Core Design Principles

## One User Owns Everything

Every piece of data belongs to a single user.

Future household and shared planning features may introduce shared ownership, but this is out of scope for the MVP.

---

## Plans Are Generated

Users do not manually create schedules.

Instead, users define:

* Commitments
* Goals
* Activities
* Constraints
* Preferences

The planning engine generates plans from those inputs.

---

## Separate Inputs from Outputs

The database should distinguish between:

**Planning Inputs**

Things the user defines.

Examples:

* Goals
* Activities
* Commitments
* Constraints

**Planning Outputs**

Things produced by the planning engine.

Examples:

* Weekly plans
* Scheduled activities
* Explanations

This separation makes replanning straightforward.

# Entities

---

# User

Represents a registered user.

## Fields

* id
* name
* email
* timezone
* locale
* created_at
* updated_at

---

# Commitment

Represents a fixed event that should normally not be moved by the planner.

Examples:

* Work
* Appointment
* Childcare
* School
* Birthday
* Soccer practice

## Fields

* id
* user_id
* title
* description
* start_time
* end_time
* recurrence_rule (optional)
* location (optional)
* source

Possible sources:

* Manual
* Google Calendar
* Apple Calendar
* Outlook

---

# Goal

Represents an outcome the user wants to achieve.

Goals influence planning but are not scheduled directly.

Examples

* Exercise four times per week
* Run a faster 5K
* Read every day
* Practice guitar

## Fields

* id
* user_id
* title
* description
* priority
* status
* start_date
* target_date (optional)

Status:

* Active
* Paused
* Completed

Priority:

* Low
* Medium
* High

---

# Activity

Represents a flexible activity that can be scheduled.

Activities support one or more goals.

Examples

* Running
* Cycling
* Strength training
* Guitar practice
* Reading

## Fields

* id
* user_id
* name
* category
* default_duration_minutes
* preferred_frequency
* preferred_days
* preferred_time_of_day
* minimum_duration_minutes
* maximum_duration_minutes
* enabled

Examples

Running

* duration = 40
* frequency = 3/week

Reading

* duration = 30
* frequency = daily

---

# Activity Goal

Many-to-many relationship between Activities and Goals.

Examples

Running

↓

Improve 5K

Cycling

↓

Ride 100 km

Strength Training

↓

General Fitness

## Fields

* activity_id
* goal_id

---

# Constraint

Represents hard scheduling rules.

The planning engine should never violate these constraints.

Examples

* No exercise after 8 PM
* Protect family dinner
* Sunday mostly free
* Maximum workout duration on weekdays

## Fields

* id
* user_id
* type
* value
* enabled

Examples

type

* max_weekday_duration
* latest_exercise_time
* protected_time
* minimum_sleep

---

# Preference

Represents soft preferences.

Unlike constraints, these may be ignored when necessary.

Examples

* Prefer morning workouts
* Prefer long rides Saturday
* Prefer reading before bed

## Fields

* id
* user_id
* type
* value
* weight

---

# Weekly Plan

Represents a generated schedule.

Users may generate multiple plans over time.

## Fields

* id
* user_id
* week_start
* status
* created_at

Status

* Draft
* Active
* Archived

---

# Scheduled Block

Represents an activity placed on the calendar.

Generated by the planning engine.

## Fields

* id
* weekly_plan_id
* activity_id
* start_time
* end_time
* confidence
* rationale

Examples

Tuesday

6:00 PM

Running

40 minutes

Reason:

"Balances recovery after Monday strength training and leaves Wednesday available for family commitments."

---

# Replanning Event

Records changes that trigger replanning.

Examples

* User missed workout
* User added appointment
* User changed priorities

## Fields

* id
* user_id
* type
* description
* created_at

---

# Plan Version

Every generated plan should be versioned.

This makes it possible to compare plans over time.

## Fields

* id
* weekly_plan_id
* version
* generated_at
* generation_reason

Examples

Initial generation

Missed workout

Vacation added

Priority changed

# MVP Notes

The MVP should only implement the entities necessary to validate the product.

Recommended implementation order:

1. User
2. Commitment
3. Activity
4. Goal
5. Constraint
6. Weekly Plan
7. Scheduled Block

Preferences, version history, and replanning events can initially be simplified if doing so accelerates delivery.

---

# Future Extensions (Out of Scope)

The schema is intentionally designed so it can evolve without breaking the core model.

Potential future additions include:

* Household accounts
* Shared calendars
* Children and dependents
* Fitness integrations (Garmin, Strava, Apple Health)
* Task management
* Projects
* Habits
* Travel planning
* Energy levels and recovery metrics
* AI memory and long-term preferences
* Notifications and reminders

These features should not influence the MVP schema unless they directly support the core planning experience.
